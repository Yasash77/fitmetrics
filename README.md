# FitMetrics + FitPulse user platform
Yasash S · 23MIC0060 · partner project: FitPulse (Maajith, 23MIC0052)

One server, two faces:
- **`/` — FitPulse app** (Yasash): accounts, guided onboarding, plans, workout logging, progress, goals, settings.
  It **collects** the user's data and **presents** results. Plans are produced by **Maajith's processing system**.
- **`/api/v1/*` — FitMetrics API** (API-key auth): workout analytics, also consumed by Maajith's FitPulse API.
  The original API console is at **`/tools.html`**, Swagger at **`/docs`**.

> **This repository holds both team projects**
> - `/` (backend, frontend, api) — **FitMetrics** (Yasash, 23MIC0060): workout analytics
> - `/fitpulse` — **FitPulse** (Maajith, 23MIC0052): energy needs, body composition, goals & progress tracking — see fitpulse/README.md
>
> Each project runs on its own and uses the other's API. Running either launcher starts the other one as its partner.

## Start the website (one step)
- **Windows:** double-click `start_windows.bat`
  (or open *Anaconda Prompt*, `cd` into this folder, run `python run.py`)
- **macOS / Linux:** `./start_mac_linux.sh` or `python3 run.py`

Then open **http://localhost:8000** (the browser opens automatically) and create an account.
Locally, plans come from the **labelled development mock** and password-reset links are shown on screen
(no e-mail server needed); both switch off when the production settings below are used.
API docs (Swagger): http://localhost:8000/docs · Stop with Ctrl+C.

`run.py` installs any missing packages, starts FitPulse from `./fitpulse` as the partner API,
and starts the FitMetrics API + website on the same server.

## Use a deployed FitPulse API instead
    Windows cmd:   set FITPULSE_BASE_URL=https://<his-url>/api/v1 && python run.py
    PowerShell:    $env:FITPULSE_BASE_URL="https://<his-url>/api/v1"; python run.py
    macOS/Linux:   FITPULSE_BASE_URL=https://<his-url>/api/v1 python3 run.py

## Deploy (optional)
Vercel (no card needed): vercel.com/new → import the repo → Root Directory **`./`** for FitMetrics.
Import the same repo a second time with Root Directory **`fitpulse`** for FitPulse.
Then set `FITPULSE_BASE_URL` on FitMetrics and `FITMETRICS_BASE_URL` on FitPulse to each other's `https://…vercel.app/api/v1` and redeploy both.
Render: New → Web Service, root `backend`, start `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
Either way one URL serves the whole site. Set FITPULSE_BASE_URL (env var) to Maajith's API URL.

## Troubleshooting
| Problem | Fix |
|---|---|
| Orange "backend isn't reachable" banner | The Python server isn't running — start it with start_windows.bat / `python run.py` |
| "Python was not found" | Use Anaconda Prompt: `python run.py` |
| Integration card says "FitPulse unavailable (503)" | Partner API not reachable — check FITPULSE_BASE_URL (expected behaviour, FitMetrics never computes maintenance calories itself) |
| Port 8000 busy | run.py automatically uses the next free port and prints it |

## FitPulse user platform

### Who does what
| Part | Owner | Where |
|---|---|---|
| Sign-up, sessions, onboarding questionnaire, plan display, logging, progress | Yasash | `backend/app/routers/platform.py`, `frontend/app.js` |
| Questionnaire definition (13 training styles, all questions) | Yasash | `backend/app/onboarding_config.json` — edit this to add questions; the UI and validation follow it |
| **Plan generation** (analyses the profile, returns the plan) | **Maajith** | his processing system, reached only through `backend/app/clients/processing.py` |
| Energy needs + goal-plan safety | Maajith | his deployed FitPulse API (`/fitness/calories`, `/fitness/goal-plan`), called server-side |
| Per-workout analysis + training balance | Yasash | FitMetrics engine in this repo (`backend/app/engine`) |

### Plan service modes (`/api/integrations/status` shows the current one)
| Setting | Mode | What users see |
|---|---|---|
| `PLAN_SERVICE_URL` set | **live** | Plans from Maajith's system, badge "Generated by Maajith's processing system" |
| `PLAN_SERVICE_MODE=mock` | **mock** | Fixed templates (`clients/mock_processing.py`), purple "Development mock — not a real recommendation" banners everywhere |
| neither | **unconfigured** | Honest "plan generation is not connected yet" message (HTTP 503). Nothing is faked. |

### Environment variables (server only — never put keys in the frontend)
| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Postgres (Neon / Vercel Postgres). Without it: SQLite (`SQLITE_PATH`), which is temporary on Vercel — the app warns users |
| `PLAN_SERVICE_URL`, `PLAN_SERVICE_KEY` | Maajith's plan endpoint base URL and the key it expects (`X-API-Key`) |
| `PLAN_SERVICE_MODE` | `mock` to enable the labelled development placeholder |
| `FITPULSE_BASE_URL`, `FITPULSE_API_KEY` | Maajith's FitPulse API (energy + goal plan) |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `PUBLIC_BASE_URL` | Password-reset e-mail. Without SMTP the reset page says e-mail isn't configured |
| `DEV_SHOW_RESET_LINK=true` | Local development only: show the reset link on screen |

### Security
scrypt password hashes · httpOnly + Secure + SameSite=Lax session cookie (only a SHA-256 of the token is stored) ·
CSRF header required on every state-changing `/api` call · login throttling stored in the database ·
every private query is scoped to the session's user id (other users' plans/workouts return 404) ·
partner keys only in server environment variables · CSP on the app page · idempotency keys on plan requests
and workout logs (double clicks never duplicate) · profile saves use a version number so a newer edit from
another tab is never overwritten silently · users can export and delete all their data.

### Plan API contract v0.1 (for Maajith's processing system)
**`POST {PLAN_SERVICE_URL}/plans`** — header `X-API-Key: <PLAN_SERVICE_KEY>`, JSON body:
```json
{
  "contractVersion": "0.1",
  "requestId": "f3c1…",                          // unique per request; safe to use for de-duplication
  "client": {"system": "fitpulse-platform", "version": "1.0.0"},
  "user": {"ref": "9a1b…"},                      // pseudonymous; no name, e-mail or birth date is sent
  "athlete": {"ageYears": 27, "sex": "female|male|not_specified", "heightCm": 166, "weightKg": 64,
              "bodyFatPct": null, "restingHr": 62, "activityLevel": "sedentary|light|moderate|active|very_active"},
  "goals": {"primary": "fat_loss", "secondary": ["strength"], "targetWeightKg": 61, "targetEvent": null, "notes": null},
  "timeline": {"weeks": 12, "targetDate": null, "startDate": "2026-10-26"},
  "experience": {"level": "beginner|intermediate|advanced|returning", "breakMonths": "6"},
  "disciplines": [{"id": "gym", "answers": {"gymFocus": "both"}}, {"id": "running", "answers": {"runDistance": "10k"}}],
  "availability": {"daysPerWeek": 4, "preferredDays": ["mon","wed"], "sessionMinutes": 60, "timeOfDay": "evening"},
  "equipment": {"locations": ["gym","pool"], "items": ["barbell"], "poolLength": "25m"},
  "constraints": {"healthCheck": "none|cleared|unsure", "injuries": null, "avoidMovements": [], "intensityPreference": null, "enjoys": null},
  "context": {"energy": {"source": "FitPulse API (Maajith)", "status": "ok", "calories": {...}, "goalPlan": {...}}}
}
```
All option values are the `value`s in `backend/app/onboarding_config.json`.

**Response** (`200`, either bare or wrapped as `{"success": true, "data": …}`):
```json
{
  "planId": "your-id", "status": "ready|processing|failed",
  "generatedBy": {"system": "maajith-processing", "version": "1.0", "isMock": false},
  "summary": {"title": "…", "overview": "…", "weeks": 12, "sessionsPerWeek": 4, "primaryDiscipline": "gym"},
  "weeks": [{"week": 1, "focus": "…", "sessions": [{
      "id": "w1s1", "day": "mon", "discipline": "gym", "title": "…", "durationMin": 60, "intensity": "moderate", "notes": "…",
      "blocks": [{"name": "Main lifts", "type": "warmup|main|accessory|intervals|circuit|stations|skill|flow|cooldown|other",
                  "rounds": 3, "workSec": 30, "restSec": 30,
                  "items": [{"name": "Back squat", "sets": 3, "reps": "8-10", "load": "RPE 7", "restSec": 120,
                             "distanceM": null, "durationSec": null, "pace": null, "zone": null, "stroke": null, "notes": null}]}]}]}],
  "guidance": ["…"], "warnings": ["…"]
}
```
Rules: `ready` plans must include `summary` and at least one week, otherwise the plan is rejected and the user sees an error
(never a half-rendered plan). Extra properties are allowed. `400/422` = profile rejected (message shown to the user);
other errors = "processing system unavailable". If you return `processing`, the app polls **`GET /plans/{planId}`**.
Optional: **`POST /plans/{planId}/feedback`** `{"sessionId", "date", "durationMin", "rpe", "completed"}` receives logged
sessions (404 is treated as "not supported").
